# Supabase account activation

The project now has Google login, email OTP, optional SMS OTP, TOTP enrollment/verification, logout, verified Google account linking, saved analyses, and durable explanations. The code is usable after the selected Supabase project is configured. Production is fail closed: absent configuration cannot turn protected routes into anonymous endpoints. Local use requires explicit `APP_ENV=development`.

1. Create or select your Supabase project. Apply `supabase/migrations/202610080001_accounts.sql` through the project's migration workflow or SQL editor. It defines user-owned explanation/history tables and an atomic 20-generation-attempt daily quota. RLS and owner filters both restrict account data. No service-role key is sent to the browser or used by the account storage adapter.
2. Enable Google in Supabase Auth. Configure your Google OAuth application and the callback URL shown by Supabase. Add the exact frontend site URL and `/account` redirect to Supabase's allowed redirects. Enable manual identity linking if you use the Link Google account button.
3. Configure custom SMTP for public email delivery. Change the email template to include `{{ .Token }}` so the code-entry flow receives a code rather than only a magic link. Set appropriate expiry and provider-side resend/attempt limits.
4. For mobile OTP, configure a supported SMS provider, target-country delivery and provider-side abuse limits. Set both `PHONE_AUTH_ENABLED=true` and `NEXT_PUBLIC_PHONE_AUTH_ENABLED=true` only after delivery is verified. Phone login is optional; Google/email remain available during SMS failures.
5. Use an asymmetric Supabase signing key (ES256 or RS256); the backend verifies JWKS signatures, issuer, audience, expiry and identity. Legacy HS256 projects must migrate their signing key before activation. JWKS are cached for five minutes, with a bounded retrieval timeout.
6. Configure the backend's `APP_ENV=staging` or `production`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and exact `CORS_ORIGINS`. Configure the frontend's `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_API_BASE` and optional private `API_INTERNAL_BASE`. Public variables are bundled at build time; rebuild the frontend when changing them.
7. Enroll Google Authenticator from Account and verify its code. Any verified enrolled factor requires AAL2 for protected backend calls. Administrator roles are granted only through trusted `app_metadata.role=admin`; administrators always require AAL2. Supabase's factor API, not editable user metadata, determines enrollment.

**Validation before public activation:** Google callback login; email and SMS delivery; wrong/expired/reused OTP rejection; resend throttling; TOTP after a fresh login; account linking without duplicate identities; logout/session expiry; one user cannot read/delete another user's analyses; database/RLS integration; daily quota; explanation replay after a worker restart. These live provider/database checks remain pending until a project is supplied. Fixed-data tests cover signature and claim rejection, owner isolation, missing configuration, MFA gating, quota denial and restart behavior.

Explanation data is JSON with precomputed selected-player SHAP drivers. It expires after one hour and never contains pickled models. Saved analyses retain the result. Schedule periodic deletion of expired explanations and usage records using the SQL examples at the bottom of the migration. SQLite under `APP_STATE_PATH` is available only in explicit local/test mode without Supabase; it is not a production fallback if account storage fails.

Self-service account deletion and additional linked email/phone management are not implemented in this increment. Supabase's project operator can perform verified account recovery/deletion; table foreign keys delete saved data with the account. Add an appropriate recovery/support route before a public beta.

Dependencies were updated to patched Next.js 16.3.6 and repaired runtime transitive packages during this step. Five development-only audit findings remain in the ESLint glob dependency chain (`braces` has no patched published version); a forced downgrade to an incompatible Next.js ESLint configuration was not applied. Production dependency audit is checked separately.
